# WhatsApp Translator

Small WhatsApp Web client with a local web UI, message history, translation, AI replies, and MCP access. Native apps for iPhone, iPad, Mac and Apple Watch live in [`apps/ios/`](apps/ios/README.md).

Production runs on [Cloudflare Containers](https://developers.cloudflare.com/containers/) behind a Worker, with the WhatsApp session and message history backed up to R2. See [Deploy on Cloudflare](#deploy-on-cloudflare). Any host that runs one long-lived Docker container with a persistent `/data` volume works too.

## Architecture

```text
WhatsApp <-> wa-bridge (Go)  <-- JSON lines over stdin/stdout -->  Rust server (apps/server)  --> SQLite in WA_DATA_DIR
                                                                         |              --> OpenAI or ChatGPT
                                                                         | HTTP, websocket, push, /mcp
                       +---------------------+-----------------+---------+----------+
                       |                     |                 |                    |
                Web UI (apps/web)     iPhone / iPad app   Mac and Watch apps   MCP clients
                                      (apps/ios)          (apps/ios)           (OAuth 2.0 + PKCE)
```

- `apps/wa-bridge/` is the only part that talks to WhatsApp. The server starts it as a child process; the wire format is in `apps/wa-bridge/protocol.go` and `apps/server/src/bridge/protocol.rs`.
- `apps/server/` is the Rust server: HTTP and websocket API (`web/`), storage (`storage.rs`, `storage/`), translation and AI (`translation.rs`, `chatgpt.rs`), voice notes (`voice.rs`), push (`push.rs`) and MCP (`mcp.rs`, `oauth.rs`).
- `apps/web/public/` is the browser client, served as static files. `apps/web/` also holds its tests and Storybook stories.
- `libs/web-extension/` is the MCP app extension, built into `dist/chats.html`, which the server embeds.
- `apps/ios/` is the Xcode project (generated by XcodeGen from `apps/ios/project.yml`) for the Apple apps, which talk to the same server API.

## Features

- Connect a WhatsApp account through QR login
- View chats and messages in a local web UI
- Browse a chat’s photos and videos in the native Gallery, with square previews and a full-screen swipe viewer
- Native iPhone Duo support: vertical bars with prioritised items on the outer display, a two-column inbox and trailing sheets on the inner display, and chats, galleries and media viewers that keep content off the hinge in book and laptop poses (details in [docs/apple/iphone-duo.md](docs/apple/iphone-duo.md))
- Send text, images, replies, and reactions
- Translate incoming and outgoing messages with OpenAI
- Listen to translated voice notes and record, preview, and send translated WhatsApp audio
- Generate AI-composed messages and AI replies in your writing style
- Per-chat translation settings, including an option to send the translation followed by the original text
- Optional AI topics in conversations and the native unified Messages feed, with matching topic names combined across chats in the unified feed
- Six original message ringtones with in-app previews, a global default, per-conversation overrides, and a silent option
- Local SQLite storage for messages, usage, and session data
- MCP endpoint with OAuth support

Details of how these behave are in [docs/features](docs/features/):

- [Messaging](docs/features/messaging.md): read receipts, translation, reply only, topics, voice notes, pasting images, gallery and app icons
- [Sign in with ChatGPT](docs/features/chatgpt-sign-in.md)
- [MCP access](docs/features/mcp.md)
- [Connection, delivery and data repair](docs/features/reliability.md)

## Required Environment Variables

Minimum:

- `WA_WEB=true`
- `WA_PASSWORD` (required for hosted/network-accessible operation)

Required for AI features, one of:

- `OPENAI_API_KEY`
- Sign in with ChatGPT from **Settings → ChatGPT account** ([details](docs/features/chatgpt-sign-in.md))

Optional:

- `WA_OPENAI_DETECTION_MODEL` default: `gpt-6-astra`
- `WA_OPENAI_TRANSLATION_MODEL` default: `gpt-6-astra`
- `WA_OPENAI_HIGH_END_MODEL` default: `gpt-6-astra`
- `WA_DEFAULT_LANGUAGE` default: `English`
- `WA_ALLOW_LOCAL_NO_AUTH=true` permits password-free development only with an explicit loopback `WA_HOST`
- `WA_HOST` default: `0.0.0.0`
- `WA_PORT` default: `3000`
- `WA_DATA_DIR` data directory for `session.db` and `messages.db`
- `WA_BRIDGE_PATH` path to the `wa-bridge` binary
- `WA_VERBOSE=true` enable verbose logs
- `WA_LOGOUT=true` clear the WhatsApp session on startup

Text AI defaults to GPT-6 Astra with low reasoning. The shared OpenAI settings override environment model choices; selecting Astra with no reasoning selection uses low. Speech recognition and speech synthesis retain their dedicated audio models.

Required for native iOS push notifications:

- `APNS_KEY_ID` Apple push notification key ID
- `APNS_TEAM_ID` Apple Developer team ID
- `APNS_BUNDLE_ID` iOS app bundle identifier
- `APNS_PRIVATE_KEY_BASE64` base64-encoded contents of the APNs `.p8` private key

The APNs key is a production secret. Keep the downloaded `.p8` file outside the
repository and provide it to the deployed service only through secret environment
variables. The authenticated `POST /api/push/test` endpoint sends a test alert to
all currently registered iPhones.

Hosted deploy recommendation:

- `WA_PASSWORD` is required on non-loopback hosts; startup fails without it
- keep `/data` across restarts: a persistent volume, or the R2 backup the Cloudflare deploy uses
- if `WA_PORT` is not set, the app uses the host's `PORT` when it sets one
- MCP OAuth supports explicitly approved local clients and ChatGPT. Dynamic client
  registration accepts loopback HTTP/HTTPS callbacks and the documented HTTPS
  callbacks on `chatgpt.com`: `/connector/oauth/{callback_id}` and the legacy
  `/connector_platform_oauth_redirect`. Other remote hosts, callback paths,
  credentials, nonstandard ports, queries and fragments are rejected. Authorization
  still requires an exact registered redirect match, password approval and S256 PKCE.

## Run Locally

Prerequisites:

- Rust 1.88, the version the production image builds with (`Dockerfile`)
- Go 1.26 or newer; `apps/wa-bridge/go.mod` asks for the `go1.27.2` toolchain, which Go downloads on first use unless `GOTOOLCHAIN=local`
- FFmpeg (required for voice-note conversion, gallery previews, and media integration tests; included in Docker)

Run:

```bash
export WA_WEB=true
export WA_HOST=127.0.0.1
export WA_ALLOW_LOCAL_NO_AUTH=true
export OPENAI_API_KEY=your_key_here

cargo run --release
```

Notes:

- If `go` is installed, `cargo` will try to build `wa-bridge` automatically.
- If not, build it manually:

```bash
npx nx build wa-bridge   # or: (cd apps/wa-bridge && go build -o wa-bridge .)

export WA_WEB=true
export WA_HOST=127.0.0.1
export WA_ALLOW_LOCAL_NO_AUTH=true
export WA_BRIDGE_PATH="$PWD/apps/wa-bridge/wa-bridge"
export OPENAI_API_KEY=your_key_here

cargo run --release
```

Then open:

```text
http://localhost:3000
```

The supported backend is the Rust app (`cargo run --release`). The `apps/web`
package is only for frontend tests and Storybook previews; it does not run a
separate Node API server.

### Run without WhatsApp or OpenAI

For UI work, screenshots and tests, fake mode needs no phone, linked account or API key:

```bash
cp .env.example .env
(cd apps/wa-bridge && go build -o wa-bridge .)
set -a; . ./.env; set +a
cargo run
```

`WA_FAKE_BRIDGE=true` makes `wa-bridge` serve a few canned chats (Spanish, Portuguese and English) instead of connecting to WhatsApp, acknowledges sends, and marks them delivered and then read; `WA_FAKE_BRIDGE=qr` shows a pairing QR code first. `WA_FAKE_AI=true` answers text AI locally: language detection guesses from the characters used and translations come back as `[Spanish → English] original text`. AI compose and styled replies return placeholder text. Topic classification needs structured AI output and reports an error in fake mode, and voice notes still need a real key.

## Tests

[Nx](https://nx.dev) runs the builds, tests and lint for every part of the repository, and caches the results so a rerun with unchanged inputs finishes in seconds. Deployable apps live in `apps/` (`server`, `wa-bridge`, `web`, `ios`, `cloudflare`), shared code in `libs/` (`web-extension`) and repository tooling in `tools/` (`tools-scripts`); each is an Nx project with its own `project.json`. The root holds the Cargo workspace and the npm workspaces, so one `npm ci` installs everything. CI runs the Go, Rust and web checks through Nx on every pull request (`.github/workflows/ci.yml`), and the `apple` workflow builds and tests the Apple apps when `apps/ios/` changes. Run the same steps locally with:

```bash
make check             # every project's checks, as CI's go, rust and web jobs run them
make check-fast        # only the projects changed since origin/main (nx affected)
make lint              # formatting, vet, clippy, prettier and types only
npx nx test server     # one task: npx nx run <project>:<target>
npx nx graph           # the project graph
```

The targets are `format-check`, `lint`, `typecheck`, `test`, `check` (the committed `chats.html` drift check), `e2e` and `build`. `make help` lists the rest. The Rust targets set `SKIP_GO_BUILD=1`, which stops `build.rs` from rebuilding the bridge when only Rust changed.

## Deploy on Cloudflare

`apps/cloudflare/` runs the image from the root `Dockerfile` on Cloudflare Containers. A Worker passes every HTTP and websocket request, including `/api/health`, to one container, which holds the WhatsApp connection:

- **One container, always on.** A Durable Object named `primary` owns the only container. A cron trigger wakes it every minute and its alarm starts the container again if it stops, so it never sleeps.
- **Data in R2.** The container disk does not survive a restart. The image's entrypoint ([`apps/cloudflare/container/entrypoint.sh`](apps/cloudflare/container/entrypoint.sh)) restores `/data` from the `babel-bridge-data` R2 bucket before the server starts, backs it up every five minutes when a file was written, added or removed (SQLite's online backup, so copies are consistent), and takes a last backup when the server stops. A crash loses at most the changes since the last backup; after one, WhatsApp may need a moment to re-establish encryption with some contacts. If the restore fails, the container exits rather than start empty, so a failed restore never overwrites the real backup. Backups are kept under `wa-data/backups/`: the six newest, plus the newest from at least a day before the current one. `wa-data/current` names the one restored; point it at an older key to roll back.
- **Updates.** After a deploy that changes the image, or a change to a secret, the Durable Object stops the container with `SIGTERM` (final backup included) and starts the new one. WhatsApp reconnects without a new QR scan.

One-time setup, with [Wrangler](https://developers.cloudflare.com/workers/wrangler/) signed in to the account (`npx wrangler login`), from `apps/cloudflare/`:

1. Create the bucket: `npx wrangler r2 bucket create babel-bridge-data`.
2. Set the secrets, each with `npx wrangler secret put <NAME>`:
   - `WA_PASSWORD` (required)
   - `OPENAI_API_KEY` if you want AI features
   - `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID` and `APNS_PRIVATE_KEY_BASE64` for iPhone push
   - optionally `WA_DEFAULT_LANGUAGE`, `WA_OPENAI_DETECTION_MODEL`, `WA_OPENAI_TRANSLATION_MODEL`, `WA_OPENAI_HIGH_END_MODEL`, `WA_VERBOSE` and `WA_BACKUP_INTERVAL_SECONDS`

   Only these names reach the server ([`container-env.ts`](apps/cloudflare/src/container-env.ts)). Secrets set before the first deploy need the Worker to exist; run step 4 first if Wrangler asks.
3. In the GitHub repository, add the Actions secrets `CLOUDFLARE_API_TOKEN` (a token with Workers Scripts, Containers, Durable Objects and R2 edit rights for the account) and `CLOUDFLARE_ACCOUNT_ID`.
4. Deploy. [`deploy.yml`](.github/workflows/deploy.yml) runs `npx nx run cloudflare:deploy` for each commit on `main` once the `CI` workflow has passed for it, skipping commits that `main` has already moved past. To deploy by hand, run the same command with Docker running. The Worker is served at `https://babel-bridge.<account>.workers.dev`; add a custom domain under the Worker's **Settings → Domains & Routes** if you want one.
5. Open the site, sign in with `WA_PASSWORD` and scan the QR code.

To keep the chats and WhatsApp session from an existing server (for example a Railway volume) instead of scanning again, seed the bucket before the first deploy. Stop the old server so the SQLite files are consistent, copy its data directory, then from `apps/cloudflare/`:

```bash
tar -czf seed.tar.gz -C path/to/old-data .
npx wrangler r2 object put --remote babel-bridge-data/wa-data/backups/2026-01-01T00-00-00-000Z.tar.gz --file seed.tar.gz
printf 'wa-data/backups/2026-01-01T00-00-00-000Z.tar.gz' > current
npx wrangler r2 object put --remote babel-bridge-data/wa-data/current --file current
```

Keep the key in the `wa-data/backups/<time>.tar.gz` form shown (any past time works); the container refuses to start from a pointer to any other key. Keep the old server stopped once the container has started, because one WhatsApp session cannot run in two places.

`CONTAINER_INSTANCE` in [`wrangler.jsonc`](apps/cloudflare/wrangler.jsonc) sets the instance size (`standard-1` by default: half a vCPU, 4 GiB memory, 8 GB disk). Logs are in the Worker's **Observability** tab in the Cloudflare dashboard.

## Run With Docker

Build:

```bash
docker build -t whatsapp-translator .
```

Run:

```bash
docker run --rm -it \
  -p 3000:3000 \
  -v whatsapp-translator-data:/data \
  -e WA_WEB=true \
  -e WA_PASSWORD=choose_a_strong_password \
  -e OPENAI_API_KEY=your_key_here \
  whatsapp-translator
```

Then open:

```text
http://localhost:3000
```

## Data

The app stores local state in the data directory, including:

- `session.db` for WhatsApp session state
- `messages.db` for chats, settings, and usage
- OAuth client registrations and bearer/refresh tokens for approved MCP clients

Treat the data directory as secret material. OAuth tokens in `messages.db` are
bearer credentials for local MCP clients; protect the volume, set `WA_PASSWORD`
on reachable deployments, and use logout or the protected OAuth client revocation
API to revoke access. Do not commit those files or any `.env` file with real
secrets.

## Diagnostics

`GET /api/diagnostics` (behind the same password as the rest of the API) returns
the server version, the deployed commit (`WA_GIT_COMMIT`) when deployed, the WhatsApp connection
state, whether AI is configured, and the last 200 warning and error log lines.
Those lines have already been through the log redaction, so they carry no chat
ids, phone numbers or message text, URLs keep only their host, and the response leaves out the account's
name, phone and QR code. Agents can use it to look at production errors without
access to the hosting logs:

```bash
token=$(curl -s -X POST "$SERVER/api/auth" -H 'Content-Type: application/json' \
  -d "{\"password\":\"$WA_PASSWORD\"}" | jq -r .token)
curl -s -H "Authorization: Bearer $token" "$SERVER/api/diagnostics" | jq
```
