# WhatsApp Translator Operating Rules

## Repository map

- `src/`: Rust server (axum). `web.rs` holds the HTTP and WebSocket routes, `storage.rs` and `storage/` the SQLite store, `translation.rs` and `chatgpt.rs` the translation providers, `mcp.rs` the MCP server, `push.rs` APNs, and `bridge/` the process and JSON protocol for the Go bridge.
- `wa-bridge/`: Go WhatsApp client (whatsmeow) that the Rust server runs as a child process. `build.rs` builds it during `cargo build` unless `SKIP_GO_BUILD` is set.
- `web/public/`: the browser app, plain JavaScript served as is with no build step. Unit tests are in `web/tests/` and run with `node --test`.
- `web/extensions/`: the MCP Apps chat UI, built with esbuild into the committed `web/extensions/dist/chats.html`, which the Rust server embeds.
- `ios/`: SwiftUI apps for iPhone, iPad, Mac, Apple Watch, and CarPlay, generated by XcodeGen from `ios/project.yml`. See `ios/README.md`.
- `docs/`: the public website. `docs/plans/` holds older design notes.

## Checks

- `make check` runs every step of the GitHub Actions `CI` go, rust, and web jobs in the same order (`make check-go`, `check-rust`, and `check-web` run one job each), and is what to run before pushing. `make check-fast` runs only the checks for the areas changed since `origin/main`. `make ci` adds the production container build, which needs Docker. `make help` lists the smaller targets.
- The Rust tests need `ffmpeg` on the path. The Go bridge needs the Go toolchain that `wa-bridge/go.mod` pins, which `go` downloads on first use.
- The Apple targets are checked only by the `apple / apple` workflow on macOS. The Apple rules below say how to work with it.

## Regenerating committed outputs

CI fails when these drift from their sources, so regenerate them in the same change:

- `web/extensions/dist/chats.html`: run `npm run build:extension` in `web/` after editing `web/extensions/src/`. `npm run check:extension` is the CI drift check.
- `ios/WhatsAppTranslator.xcodeproj`: regenerate with XcodeGen 2.45.4 after editing `ios/project.yml`, using the commands in `ios/README.md`. The `apple / apple` check fails when the committed project differs.
- `web/public/sounds/`: re-render the message tones with `python3 scripts/generate-message-tones.py`.

## TestFlight release completion gate

- TestFlight builds of `WhatsAppTranslator` (iOS/iPadOS) and `BabelBridgeMac` (macOS) come from the Xcode Cloud workflow `Main – TestFlight (internal)` when a pull request merges to `main`.
- Agents must not bump `CURRENT_PROJECT_VERSION` and must not upload to TestFlight by hand. Xcode Cloud assigns the build number from the Next Build Number in App Store Connect. A manual upload collides with those numbers unless Next Build Number is raised first.
- A change counts as shipped when the Xcode Cloud build for its merge commit succeeds. The handoff reports that Xcode Cloud build number. App Store Connect processing and TestFlight availability checks are not required for completion.
- If the Xcode Cloud build for the merge commit does not succeed, do not describe the request as fully released; report the exact blocker and which platform remains outstanding.
- `MARKETING_VERSION` is still bumped deliberately when shipping a new version.

## Apple build and release workflow

- GitHub Actions runs the `apple` workflow on pull requests and pushes to `main`. The stable check is `apple / apple`. It builds `WhatsAppTranslator` and `BabelBridgeMac` with signing disabled and runs `WhatsAppTranslatorUnitTests` and `BabelBridgeMacTests` when `ios/`, `web/public/sounds/`, or `.github/workflows/apple.yml` changes, and passes without a build on every other change, so branch protection can require it. The commands are in `ios/README.md`. Local agent builds follow the next rule.
- Xcode Cloud workflow B, `Main – TestFlight (internal)`, archives merges to `main` for internal TestFlight. The one-time setup for that workflow is in `ios/README.md`. Pull-request build and test stays on the GitHub Actions check.
- Local sessions on a Mac: manual builds in the Xcode application stay appropriate for local debugging. Always use the Xcode application through Computer Use for local Apple builds, tests, archives, and signing. Do not use command-line xcodebuild or the build runner for these actions.
- Local sessions on a Mac: run storage preflight before building, use task-owned DerivedData and serial local tests, and preserve release archives and symbols.
- Cloud sessions (Linux containers, including Claude Code on the web and Codex cloud) have no Xcode, no simulator, and no Computer Use, so they cannot build, test, or archive the Apple targets and must not try. For a change under `ios/`, push it and rely on the `apple / apple` check. If that check fails, read the failing `build (ios)` or `build (macos)` job log through the GitHub API, fix the cause, and push again. XcodeGen cannot run on Linux either, so a `project.yml` edit cannot be checked against the committed `WhatsAppTranslator.xcodeproj` locally: edit both by hand, and say in the pull request that the project drift check has only run in CI.
- iPhone Duo behaviour lives in `ios/WhatsAppTranslator/Design/FoldableDisplaySupport.swift` behind `#if compiler(>=6.4)` and runtime availability checks, with the pure rules in `FoldableLayoutModel.swift`. Keep every use of an iOS 27 or 27.1 API inside those guards so Xcode 26.6 keeps building, keep `FoldableLayoutModel.swift` free of SwiftUI so `FoldableLayoutTests` runs in both unit-test targets, and build or archive with Xcode 27.1 or later when the change must be checked on iPhone Duo. Do not raise the GitHub Actions Xcode pin until the `macos-26` runner image provides that Xcode release.
