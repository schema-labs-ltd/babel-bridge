# WhatsApp Translator Operating Rules

## Working Contract

- Carry an implementation request through investigation, scoped changes, and verification. Make routine, reversible decisions using repository conventions; do not stop at a plan or ask again for authorization already given.
- Opening a PR needs no separate request: when implementation work is complete and verified, push the branch, open a PR, and keep it moving through CI and review. Merge it as **Risk Tiers & Merging** describes; merging a PR that way also authorizes the Railway deploy of `main` and the Xcode Cloud TestFlight build that follow it. Closing or force-pushing a PR still needs explicit authorization.
- In a PR description, fill in [the PR template](.github/pull_request_template.md): the problem, resulting behavior, risk tier, verification with real command output, how to revert, and migration or configuration implications.

## Repository map

- `src/`: Rust server (axum). `web/` holds the HTTP and WebSocket routes, `storage.rs` and `storage/` the SQLite store, `translation.rs` and `chatgpt.rs` the translation providers, `mcp.rs` the MCP server, `push.rs` APNs, and `bridge/` the process and JSON protocol for the Go bridge.
- `wa-bridge/`: Go WhatsApp client (whatsmeow) that the Rust server runs as a child process. `build.rs` builds it during `cargo build` unless `SKIP_GO_BUILD` is set.
- `web/public/`: the browser app, plain JavaScript served as is with no build step. `app.js` defines the `WhatsAppClient` class and installs its methods from `app/*.js`, one module per area, so add a method to the module for its area. Unit tests are in `web/tests/` and run with `node --test`.
- `web/extensions/`: the MCP Apps chat UI, built with esbuild into the committed `web/extensions/dist/chats.html`, which the Rust server embeds.
- `ios/`: SwiftUI apps for iPhone, iPad, Mac, Apple Watch, and CarPlay, generated by XcodeGen from `ios/project.yml`. See `ios/README.md`.
- `docs/`: the public website. `docs/plans/` holds older design notes.

## Checks

- Nx 24 runs every build, test, and lint task. Each project has a `project.json`: `server` (the Rust crate at the repository root), `wa-bridge`, `web`, `extension` (`web/extensions`), `tools-scripts`, and `ios` (the API contract check). `nx.json` holds the shared inputs and caching; `.nxignore` lists files no task reads. Add or change a check in the project's `project.json`, and keep `ci.yml` and the `Makefile` calling Nx targets rather than raw commands.
- `make check` runs every project's checks through Nx, the same targets the GitHub Actions `CI` go, rust, and web jobs run (`make check-go`, `check-rust`, and `check-web` run one job each), and is what to run before pushing. `make check-fast` runs `nx affected` against `origin/main`. Nx caches results; `npx nx run <project>:<target> --skip-nx-cache` forces a rerun. `make ci` adds the production container build, which needs Docker. `make help` lists the smaller targets.
- The Rust tests need `ffmpeg` on the path. The Go bridge needs the Go toolchain that `wa-bridge/go.mod` pins, which `go` downloads on first use.
- The Apple targets are checked only by the `apple / apple` workflow on macOS. The Apple rules below say how to work with it.

## Regenerating committed outputs

CI fails when these drift from their sources, so regenerate them in the same change:

- `web/extensions/dist/chats.html`: run `npm run build:extension` in `web/` after editing `web/extensions/src/`. `npm run check:extension` is the CI drift check.
- `ios/WhatsAppTranslator.xcodeproj`: regenerate with XcodeGen 2.45.4 after editing `ios/project.yml`, using the commands in `ios/README.md`. The `apple / apple` check fails when the committed project differs.
- `web/public/sounds/`: re-render the message tones with `python3 scripts/generate-message-tones.py`.

## TestFlight release completion gate

- TestFlight builds of `WhatsAppTranslator` (iOS/iPadOS) and `BabelBridgeMac` (macOS) come from the Xcode Cloud workflow `Main – TestFlight (internal)` when a pull request merges to `main`.
- Agents must not bump `CURRENT_PROJECT_VERSION` and must not upload to TestFlight by hand. Xcode Cloud assigns the build number from the Next Build Number in App Store Connect. A manual upload collides with those numbers unless Next Build Number is raised first.
- A change counts as shipped when the Xcode Cloud build for its merge commit succeeds. The handoff reports that Xcode Cloud build number. App Store Connect processing and TestFlight availability checks are not required for completion.
- If the Xcode Cloud build for the merge commit does not succeed, do not describe the request as fully released; report the exact blocker and which platform remains outstanding.
- `MARKETING_VERSION` is still bumped deliberately when shipping a new version.

## Apple build and release workflow

- GitHub Actions runs the `apple` workflow on pull requests and pushes to `main`. The stable check is `apple / apple`. It builds `WhatsAppTranslator` and `BabelBridgeMac` with signing disabled and runs `WhatsAppTranslatorUnitTests` and `BabelBridgeMacTests` when `ios/`, `web/public/sounds/`, or `.github/workflows/apple.yml` changes, and passes without a build on every other change, so branch protection can require it. The commands are in `ios/README.md`. Local agent builds follow the next rule.
- Xcode Cloud workflow B, `Main – TestFlight (internal)`, archives merges to `main` for internal TestFlight. The one-time setup for that workflow is in `ios/README.md`. Pull-request build and test stays on the GitHub Actions check.
- Local sessions on a Mac: manual builds in the Xcode application stay appropriate for local debugging. Always use the Xcode application through Computer Use for local Apple builds, tests, archives, and signing. Do not use command-line xcodebuild or the build runner for these actions.
- Local sessions on a Mac: run storage preflight before building, use task-owned DerivedData and serial local tests, and preserve release archives and symbols.
- Cloud sessions (Linux containers, including Claude Code on the web and Codex cloud) have no Xcode, no simulator, and no Computer Use, so they cannot build, test, or archive the Apple targets and must not try. For a change under `ios/`, push it and rely on the `apple / apple` check. If that check fails, read the failing `build (ios)` or `build (macos)` job log through the GitHub API, fix the cause, and push again. XcodeGen cannot run on Linux either, so a `project.yml` edit cannot be checked against the committed `WhatsAppTranslator.xcodeproj` locally: edit both by hand, and say in the pull request that the project drift check has only run in CI.
- iPhone Duo behaviour lives in `ios/WhatsAppTranslator/Design/FoldableDisplaySupport.swift` behind `#if compiler(>=6.4)` and runtime availability checks, with the pure rules in `FoldableLayoutModel.swift`. Keep every use of an iOS 27 or 27.1 API inside those guards so Xcode 26.6 keeps building, keep `FoldableLayoutModel.swift` free of SwiftUI so `FoldableLayoutTests` runs in both unit-test targets, and build or archive with Xcode 27.1 or later when the change must be checked on iPhone Duo. Do not raise the GitHub Actions Xcode pin until the `macos-26` runner image provides that Xcode release.

## Server and app API contract

- `fixtures/api/` pins the HTTP and WebSocket JSON that the Apple apps decode. `responses/` is written by the Rust test `api_contract` (`src/api_contract.rs`), which drives the real router; `requests/` holds the bodies the apps send, which the server must accept.
- After an intended API change, run `UPDATE_FIXTURES=1 cargo test api_contract`, review the fixture diff, update `ios/WhatsAppTranslator/Models/APIModels.swift`, then run `scripts/check-api-contract.sh`. That script builds `APIModels.swift` with `ios/APIContract/APIContractCheck.swift` and decodes every fixture; it runs on Linux with a Swift 6 toolchain, and the `CI / api-contract` job runs it on every pull request.
- Keep `APIModels.swift` and `MessageTone.swift` free of Apple-only frameworks so the check keeps building on Linux. A new fixture needs a matching check in `APIContractCheck.swift`, or the script fails.

## Risk Tiers & Merging

The change sets the tier, not the author. `.github/workflows/risk-gate.yml` labels every PR `risk:low`, `risk:medium`, or `risk:high` from the files it changes, using the path lists in `tools/scripts/risk-tier.mjs`.

| Tier   | Typical change | Needs before merge |
| ------ | -------------- | ------------------ |
| Low    | Docs, the website in `docs/`, tests, screenshots | Checks green, Codex and Copilot reviews answered |
| Medium | Ordinary server, bridge, web app and Apple app changes | The above, plus a fresh-context review before the PR opens |
| High   | CI, agent rules and hooks, dependencies and toolchains, deploy config, storage schema and migrations, sign-in, OAuth and MCP permissions, log redaction, APNs push, the API fixtures the apps decode, Apple signing and release | The above, plus `/security-review`, plus a person approving the `Human approval` check |

- The label is a floor. Raise the tier, and say why in the PR's **Risk** section, when a change can leak message content, phone numbers or tokens, let a request skip sign-in, lose stored messages, or break the shipped apps outside the listed paths. Never lower it. A PR you raise to high does not get the `Human approval` check, so leave auto-merge off and ask the requester to merge it.
- Before opening a medium or high PR, review the diff with fresh context: use the `code-review` skill, or a reviewer subagent given only the request and the diff. For high, also run the `security-review` skill. Fix each finding or record why not. Delegating these reviews is requested here, so it counts as permitted.
- Wait until Codex and Copilot have reviewed the latest commit and every review thread is fixed, or answered with a reason, and resolved. Then enable auto-merge (squash) with the GitHub `enable_pr_auto_merge` tool instead of merging directly. GitHub merges through the merge queue once the required checks pass.
- Before pushing another commit to a PR with auto-merge on, disable auto-merge, and enable it again once the new commit has been reviewed.
- A high PR stays open until a person approves its `Human approval` run in the Actions tab; each new push or edit to the PR (title, description, base) needs a fresh approval, so finish the description before asking. Tell the requester in one line that it is waiting on them. Never approve that environment yourself, and never change rulesets, branch protection, environments, `risk-gate.yml`, or `risk-tier.mjs` to get a PR through.
- Cap review rounds at three. A round is a push that answers review findings. If findings remain after the third, stop pushing and ask the requester whether to change the approach, listing what is still open.
- When a finding is real, fix every instance of that class of bug in the diff, not only the line flagged. Move a comment that keeps recurring into `AGENTS.md`, `REVIEW.md`, a lint rule, or a test.
- If a merged PR breaks `main` or production, open a revert PR (`git revert`) first and fix forward afterwards. The revert follows the same tier as the original PR.
- Do not split or reshape a change to lower its tier. To change the tiers, edit the path lists in `risk-tier.mjs` and `risk-tier.spec.ts` together; `node --test tools/scripts/*.spec.ts` (or `make scripts-test`) runs the specs.

## File size limit

- A Lefthook pre-commit hook (`lefthook.yml`, `scripts/check-file-size.sh`) blocks any commit that stages a hand-written text file over 5,000 tokens, counted as bytes / 4 (20,000 bytes). Install it once per clone with `npx lefthook install` (or `lefthook install`).
- It checks only staged files, so an existing oversized file blocks the commit only when it is edited. When that happens, split the file as the hook's message describes, in the same commit; do not bypass the hook with `--no-verify` or trim content to fit.
- Binary files and files marked `linguist-generated` in `.gitattributes` (lockfiles, `web/extensions/dist/`, Xcode project and asset catalog files) are skipped. Mark new generated files there.
- Run `scripts/check-file-size.sh $(git ls-files)` to list every file currently over the limit.
